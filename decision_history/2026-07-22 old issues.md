feature-plugin re-implementation.

behaviours, and design traps — so a rewrite does not rediscover them the hard way.

Each bullet is one issue, tagged with the area it touches and the session it came from.

## Issues

- **[recording]** PLAN.md described `h.stdin.raw` as "the unrecorded variant" — an AI transcription error. The user's actual intent was `.raw` as the raw-binary counterpart of `h.raw` (control characters/escapes intact, no encoding step); recording is orthogonal, controlled solely by the existing `record=` parameter (default `True`), not baked into which layer you write through. *(Fix std.in.raw)*
- **[pty]** The AI had invented a third stdin layer, `h.stdin.buffer.write(bytes)`, distinct from `h.stdin.raw`. For a PTY there is no buffering distinction (unlike a real `sys.stdin.buffer` vs a raw fd), so `.buffer` and `.raw` would have done identical jobs — the design should collapse to exactly two layers: text `write(str, record=True)` and byte `.raw.write(bytes, record=True)`. Deleted the redundant `.buffer` class in `src/quahog/session.py`. *(Fix std.in.raw)*
- **[recording]** Before the fix, `README.md`'s secret-feeding example wrote `h.stdin.raw.write(secret)` with no `record=False`. Because `.raw` previously hardcoded `record=False` internally, the example accidentally worked; once `.raw` was corrected to record by default (same as every other input path), that same example would have written the secret straight into the `.cast` recording file. Fixed to `h.stdin.raw.write(secret, record=False)` — a reminder that secret-suppression is the caller's responsibility via explicit `record=False`, never an implicit property of a "raw" write. *(Fix std.in.raw)*
- **[exec]** The old `_Stdin.raw` implementation (pre-fix) also skipped `_check_fg_exec()`, the check every other input path performs before writing to the PTY. That meant a write via `.raw` could race a foreground exec that currently owns stdin. Fixed by making `.raw.write` call `_check_fg_exec()` like `.write()`/`send()`/`sendline()` do. *(Fix std.in.raw)*
- **[exec]** `src/quahog/sub_sessions.py`'s `_ExecStdin` (the exec-handle counterpart of session `_Stdin`) had the same invented `.buffer` layer; renamed to `.raw` so the exec handle's stdin shape mirrors the session's after the correction. *(Fix std.in.raw)*
- **[osc]** xterm.js's OSC 1 handling (`setIconName`) only stores the icon-name string internally — it emits no event and exposes no public getter, so of OSC 0/1/2 only the title is actually retrievable from application code (via `onTitleChange`, which fires for OSC 0 and OSC 2). Discovered while implementing OSC icon/title support for the console toolbar; xterm.js does *not* "already support" the icon half despite parsing it. *(Console UI tweaks)*
- **[osc]** xterm.js runs custom OSC handlers in last-registered-first order, so a custom handler for OSC 0/1 must return `false` to fall through to xterm's own built-in title handling rather than short-circuiting it — this is how the widget read the icon name off its own handler without clobbering xterm's title parsing. *(Console UI tweaks)*
- **[osc]** xterm.js's `term.write()` parses escape sequences asynchronously; reading the DOM immediately after a `write()` call in a browser test showed nothing updated, which looked like a bug but was just the write queue not yet flushed — a wait/poll before asserting on parsed OSC state is required. *(Console UI tweaks)*
- **[widget]** Bug found and fixed in the toolbar's OSC title/icon display: when only an icon name was set (no title), the tooltip redundantly repeated the same text already shown in the bar; fixed by comparing the tooltip text against what is actually displayed rather than always concatenating title+icon. *(Console UI tweaks)*
- **[widget]** CSS bug found and fixed: setting `display: none` on the empty OSC-title `<span>` collapsed the toolbar's spacer/layout, shifting other elements; fixed by keeping the span always present in the DOM and hiding only the separator via a `:empty` selector instead of hiding the span itself. *(Console UI tweaks)*
- **[widget]** Design trap: the "stdin closed" toolbar indicator has to represent two distinct states, not one — after process exit, keystrokes go nowhere because the widget itself drops them, but during a foreground exec, typing still reaches the running command because `_ExecStdin` writes to the same PTY the console does; the indicator only labels the exec state, it must not (and does not) block input then. *(Console UI tweaks)*
- **[widget]** User course-correction reverted a fully-implemented and browser-verified feature: the OSC icon-name toolbar display was built, tested against the real xterm.js bundle, then removed entirely because the embedded console widget cannot be "iconified"/minimized, so an icon name has nowhere meaningful to display. The stdin badge was also renamed from "stdin closed" to "Input disabled" since "closed" was misleading for the exec sub-state (input is redirected, not actually closed). *(Console UI tweaks)*
- **[exec]** Confirmed dead code noted but deliberately left unfixed (out of scope for the UI-tweak task): in the OSC 2607 `X` handler in `src/quahog/session.py` (~line 369), the `fg_exec` clear is gated by `if es.background:`, but `fg_exec` is only ever set for foreground execs, so `st.fg_exec == eid` can never be true inside that branch. - **[pty]** Empirical/platform finding used to justify the (later superseded) OSC-frame muxing scheme: on Linux, `tty_write()` holds `tty->atomic_write_lock` across a whole `write()` syscall, so bytes from one `write()` are never interleaved with another writer's on the same tty (macOS/BSD serialize similarly) — but this atomicity is per-`write()`-call, not per logical output, so a large `printf` or stdio buffer flushed across multiple `write()`s can still be split by another writer's frame in between. *(Milestone 4)*
